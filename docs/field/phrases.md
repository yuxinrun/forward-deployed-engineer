# 话术与模板：把话说明白，把责任写清楚

这一章不讲道理，只给句子。

现场真正贵的不是 bug，是**误解**。一句"这个我们支持"值多少钱，取决于它后面有没有跟着"在什么环境、什么数据、什么口径下支持"。有一条从业者总结值得贴在显示器边上：

<div class="mp-quote">
  <p>"Our system does not improvise. When we misunderstand… that misunderstanding surfaces as a failure."（我们的系统不会即兴发挥。我们理解错了，那个错误会以一次失败的形式暴露出来。）反过来也成立："A system that can improvise around a bad encoding will never tell you the encoding was bad."（能在坏编码上糊过去跑起来的系统，永远不会告诉你编码是坏的。）</p>
  <footer>Vinoo Ganesh，前 Palantir <code>[B]</code>。这一章的所有模板都在做同一件事：让误解必然报错，而不是必然被糊过去</footer>
</div>

## 一、合同还没签：反问雇主（也反问自己）

这一组问题不是显得聪明用的，是用来提前发现"这份工作会在第三个月让你想辞职"的结构原因。

| 问什么 | 怎么问出口 | 答案里听什么 |
| --- | --- | --- |
| 驻场周期 | "单次驻场是按周排还是按月排？" | 按月排的基本是实施项目，不是这一行说的 FDE `[C]` |
| 决策权 | "POC 到生产这一步，谁拍板、什么时候拍？" | 答不出来 = POC 成功后没人接，最常见的死法 |
| 写不写代码 | "你们的 FDE 过去两周打开过 IDE 吗？" | 原话出自前 Palantir FDE 的哨兵问题 `[B]`；答"他们主要负责协调"就危险了 |
| 反馈去哪 | "现场发现的东西，进产品路线图的机制是什么？" | 答"会同步给产品"但没有具体流程 = 十几页文档三个月没人回 |
| 差旅上限 | "差旅比例写在合同或 offer 的哪一句？" | 同一家公司两份 JD 能写 25% 和 50% `[A]`/`[B]`，口头承诺不算数 |
| 验收口径 | "尾款挂在什么条件上？" | 挂"效果提升 30%"这种形容词，等于永远收不到 |
| 失败定义 | "这个项目失败的时候，谁会第一个知道？" | 答不出来说明没人真的为结果负责 |

::: tip 反向提醒
在国内语境里加一条：**"这个岗位挂在交付序列还是研发序列？"** 同名字段在集成商的研发部里叫"研发部前沿部署工程师"，月薪 8–10k，职责最后一行是"完成领导交办的其他工作" `[A]`/`[B]`——这不是 FDE 岗位，是驻场人力的另一种写法。看清了再谈，别看清了再失望。
:::

## 二、进场第一周：名词和动词清单

不要在这一周写代码。这一周的交付物是一张表，它决定了后面所有沟通的成本。

```text
术语表（客户口径）
------------------------------------------------------------
词 / 他们的说法      | 谁在用这句话    | 我们原本的理解 | 差异
------------------------------------------------------------
"跑不通"             | 车间班组长      | 系统报错       | 实际指"卡在第 3 步没人填"
"报表"               | 财务            | BI 看板        | 指每月导出的一次 Excel
"客户"               | 客服中心        | 终端用户       | 指开户主体，不是使用人
"及时"               | 运维            | P95 < 2s       | 指"领导问起来能答"
```

填这张表的唯一标准是：**你在这张表上问出的问题，听起来越蠢越好。** 一个 FDE 在第一周被旁观者评价为"好像什么都没干"，是正常现象。

## 三、POC 阶段：失败条件声明（最省钱的三行字）

试点开始前，把下面这段发出去。它的作用不是保护自己，是让"要不要继续"这个决定不再靠感觉。

```text
本次试点的判定标准（三行）

1) 成功条件：在【真实生产数据】上，【指标名】达到【阈值】，
   且【N】个真实用户在【两周】内每周主动使用 ≥【X】次。

2) 失败条件（任一命中即停止追加投入，不延长试点）：
   - 关键数据无法在【日期】前取得；
   - 单位调用成本超过【金额】且无可行降级方案；
   - P99 延迟超过【X 秒】，业务方明确不接受。

3) 谁拍板：【姓名/角色】，评审时间【日期】。
   本文件发出后 3 个工作日内无人提出异议，即视为认可上述三条。
```

三条里最重要的是第三条。**没有具名决策人的 POC，结局一定是"再看一下"，然后无限延长。**

## 四、范围蔓延：三句话挡住"顺手加个小功能"

甲方那句"再加个按钮就行"不是恶意，是善意的好奇。挡住它的正确方式不是拒绝，是把它变成一条有价格的记录。

```text
① "可以做。这句话我理解成【复述一遍需求】，对吗？"
② "它会影响已经承诺的【交付物/日期】，影响大概是【X 天】。
    我记在变更单里，麻烦【角色】确认一下要不要现在做。"
③ "如果现在不做，【业务动作】还能照常进行吗？"
```

第三句通常会把需求自动排序。绝大多数"必须今天加"的功能，在这句之后会自己退到下一期——而且不会得罪任何人，因为它是你自己退的，不是你被拒的。

变更单最小字段（够用就行，别设计流程）：

| 字段 | 为什么要写 |
| --- | --- |
| 谁提出的（具名） | "大家都觉得"是最贵的状态 |
| 一句话需求 + 一句话业务动作 | 防止功能与目的在传递中脱钩 |
| 影响（天/元） | 让代价出现在决策之前而不是验收之后 |
| 是否影响已签验收条款 | 这一栏决定它要不要走商务 |
| 确认人 + 确认时间 | 三个月后唯一的救命字段 |

## 五、周报：三段式，别写"完成了什么"

汇报纪律有一条被反复提到的原则：先结论后背景（BLUF），文档要能被下一个人接手，而不是写得漂亮 `[C]`。国内交付环境还额外要求"日报台账、当日闭环"——同一个意思：记录本身是交付物。

```text
【结论】本周系统被 34 人使用，人均 6 次；2 个坏例，1 个已修。
【变化】切块策略从 500 字改为按标题分段，召回从 0.61 → 0.78。
【请求】需要 @某某 在周四前确认：财务报表口径算哪个字段。
        不确认的后果：验收时"准确性"无法度量。
```

三段各自的作用是：结论让领导能转发，变化让产品团队能接走，请求让责任落到具体人头上。**第三段最容易被省掉，也最值钱。**

## 六、采用度三件套：唯一能救你的数字

翻车的项目通常不缺准确率，缺的是有人用。可照抄的口径来自 BBVA 案例（10 万+ 席位、周活 &gt;70%、人均每周省约 3 小时）`[A]`：

| 报什么 | 单位 | 为什么是它 |
| --- | --- | --- |
| 覆盖人数 | 开通席位 / 目标人数 | 说明"不是只有你一个人在用" |
| 活跃率 | 周活 / 开通席位 | 唯一能拆穿"上线了"这个数字的词 |
| 单人省时 | 小时 / 周 / 人 | 让财务能听懂，让续约能算账 |

反面清单（这些数字不能救你，只会让你显得在自证）："上线了 N 个用例""做了 M 个 demo""接入了 K 个系统"。这正是 MIT 那份报告批评的那类口径 `[A]`——高管说成功、员工说没人用。

## 七、生产化与安全评审：把最后两周挪到第二周

最常见的死法之一：安全评审在最后两周才第一次上桌 `[C]`。在国内它不是延期，是终止。提前问三句：

```text
1) 数据流向：哪些字段会离开客户机房？离开之后存在哪里、多久删除？
2) 谁能动：模型/运维/厂商各需要什么权限，最小集是什么，怎么回收？
3) 怎么留痕：一次回答能否复盘？日志保留多久？由谁的审计系统持有？
```

这三问就是等保与内网环境的白话版。答不出第 1 条的方案，不要提交评审——它会以"回去重来"的方式答复你。

## 八、验收条款：把形容词换成句子

国内一个交付复盘里最常见的坑，是合同里写着"效果提升 30%"这类没法验收的话 `[C]`。同一条款写成可验收，只需要三处改动：

| 不能验收的写法 | 能验收的写法 |
| --- | --- |
| 系统显著提升客服效率 | 客服单笔工单平均处理时长由 A 降至 B，抽样 200 单，由【角色】于【日期】复核 |
| 支持多种数据源接入 | 支持【系统名】的【N】张表，字段映射清单见附件并由【角色】签字 |
| 回答准确率 ≥ 90% | 在【评测集名】（N 条、由业务方共同标注）上，指标【名称】≥【阈值】；集样本与判定规则一并归档 |
| 系统稳定运行 | 连续 30 天，P99 延迟 ≤【X】秒、无 S1 事故，告警记录由双方共同查阅 |

四条铁律：**具名评测集、具名验收人、具体日期、可复现的判定方式。** 少任何一条，尾款就会变成一次谈判。

## 九、出问题那天：把事故写成坏例

```text
不要写："系统出现异常，已修复。"
要写："【日期】在【场景】下发生【现象】，影响 N 个用户 / M 单业务。
       根因：【一句话】。已修：【动作】。
       新增坏例：评测集追加 1 条（编号 XX），本条不修复会导致【后果】。
       下一次验证：【日期】，用【方法】。"
```

同一件事用第二种方式记录，客户更容易接受，评测集也长了一行。**事故要追责，坏例是资产。**

还有一句固定句式，用于承认判断错了（这一行的节奏本来就是反复被推翻）：

```text
"这个判断错了，错在 X。我下周用 Y 验一次，结果周三前给你。"
```

不解释动机、不谈客观困难、不给新承诺——只给一次可验证的补救。这三件事在客户耳朵里听起来是同一个东西：**可控**。

## 十、国内特有的四句确认

在央国企与甲方环境里，流程本身就是交付物的一部分。四句确认，最好在进场第一周就说出口：

| 说什么 | 它在防什么 |
| --- | --- |
| "适配清单我按『实测过 / 声称支持 / 未知』三态写，未知项风险由谁承担？" | 四套指令集 × 多种国产 OS × 多种国产数据库，逐条核实，"声称支持"是最大的一类坑 `[B]` |
| "阶段一的交付物是《信创兼容性测试报告》和《国密算法集成方案》，需要 1–2 个月。" | 把适配当交付物排进计划，而不是当可行性问题临时补 `[B]` |
| "验收分节点：模块初验、整体终验、质保期尾款。终验需要哪位领导签字？" | 尾款挂在验收上，而终验现场可能"新换了一位分管领导" `[C]` |
| "报价留 20%–30% 的缓冲，用于封网、节假日和评审等待。" | 传统软件交付的通行缓冲口径 `[A]`；不写出来就只能自己吞 |

## 十一、可直接开口读的英文句子

外企面试与跨国客户现场最常被需要的那四句，都是原文照录，背下来比临场组织语言安全：

```text
"Can we write down what failure looks like before we start?"
"Who signs off on this metric, and by when?"
"Spend a week inside a company… learn their nouns and verbs."   ← 转述 Ganesh 的方法 [B]
"What happens to this insight inside your product team?"
```

第四句是判断一家公司 FDE 成色的最好用的一句，它同时问出了流程、文化和你自己未来一年的工作体验。

## 这章的用法
