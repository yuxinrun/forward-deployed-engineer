# 国内现场

海外那一层的难点是差旅和生产化。国内这一层的难点是三件完全不同的事：**跑不起来、出不去、收不到钱。** 这一页只讲这三件事，并且只讲有出处的部分。

## 一、出不去：私有化在国内不是选项

先看客户结构，再看技术方案。原话说得很直白："数据安全服务的客户——尤其是金融、政务、运营商——不可能把自己的库表结构、访问日志、敏感数据样例送到公有云大模型上。这就要求模型能私有化部署在客户环境内，并且适配国产算力底座。" `[B]`

这一句在三个行业里是<b>法律红线</b>级别的表述："金融、政务、医疗、军工——这些行业的数据不出域是法律红线" `[C]`。落到交付形态上就成了：

- **升级也走离线包**："无论是初始部署还是后续升级，都通过离线包完成，从根本上杜绝了数据外泄的任何可能通道" `[C]`
- **开发环境也在客户侧**：券商案例是"代码不能出机房，开发机在客户侧、评审靠远程" `[C]`——这是"私有化 + 信创"下最典型的一条约束，它同时改变了你的协作方式
- **甲方侧的真实代价**：本地化部署"本来是政务、金融这类敏感行业的选项，代价是硬件、运维、升级全部自己扛。对一家连专职 IT 都没有的小公司来说，系统上线那天，往往就是无人维护的开始" `[C]`

有从业者给过一组估算："在约 87% 的使用场景里，直接调 API 都比自建更划算……而自建一套同等算力的集群，首年投入至少 200 万。" `[C]` **这是单方测算，没有第三方来源，本站只能写成"有从业者估算"**——但它指出的方向是对的：很多私有化项目不是技术选择，是合规强制，所以"划不划算"这个问题常常没人有资格问。

## 二、跑不起来：信创适配是逐条核实，不是看宣传

上面那张栈图的关键句是这句："一是适配清单是硬门槛……每一项都需要逐条核实兼容性列表，而非看宣传口径。" `[B]` 三条最容易被忽略的后果：

**监控体系要重建。** 在"国产CPU（鲲鹏、飞腾）、国产OS（麒麟、统信UOS）、国产数据库（达梦、人大金仓、OceanBase、openGauss）组成的异构环境里，原有的监控探针可能无法运行，原有工具的适配清单里没有这些组件" `[B]`。也就是说：<b>P0 那张"日志/指标/告警"的交付清单，在国内要重写一遍。</b>

**境外工具链直接不合规。** "JFrog Artifactory、Sonatype Nexus 等境外商业软件无法满足信创合规要求——不支持国产芯片（飞腾、鲲鹏）、国产操作系统（麒麟、统信）和国产数据库……同时，镜像数据的存储加密和传输加密不符合国密标准，无法满足等保合规和金融监管要求" `[B]`。

**没有 API 的老系统，用 GUI 打通。** 一条真实做法："通过API+GUI双轨自动化打通无API接口的老旧信创系统" `[B]`。这句话值得翻译成人话：<b>有的系统只能像人一样点，不能像程序一样调。</b>

而"跑起来"三个字在国内有更高的及格线——"信创适配并非\'能跑起来\'即可，而是需要在国产环境下达到生产级可用的性能标准" `[C]`。有从业者把最常见的失败顺序写成了三段："模型选好了，硬件买回来了，部署上去跑不通。或者跑通了，性能只有理论值的30%。或者性能达标了，等保测评过不了" `[C]`；同一人还补了一句更扎心的观察："90%的企业，在\'选什么模型\'这个问题上纠结了两三个月，却在\'用什么硬件、怎么适配信创环境\'这个真正决定成败的问题上，只花了一个下午" `[C]`。

## 三、过不了那一关：等保与审计先看数据流向

政务私有化的实操原话，是本页最实用的一段：

<div class="mp-quote">
  <p>"很多单位第一步就走偏：以为租几张卡、装个开源模型就叫私有化。真到了等保测评和审计环节，才发现网络隔离没做、日志没留、数据流向说不清，照样过不了关。所以私有化部署第一步永远是画清楚\'数据在哪里、谁能动、怎么留痕\'，算力只是承载这件事的底座。"</p>
  <footer>IDC 服务商的避坑文 <code>[C]</code>——立场是卖资源，但这段的顺序是对的</footer>
</div>

"三张图"在国内的具体版本：**数据在哪里、谁能动、怎么留痕**。它们分别对应数据驻留、权限模型、审计日志——也就是海外那一层里"数据驻留、SOC 2 审计、代码不出机房"这三条硬约束的国内实现 `[A]`。国内 JD 也确实把这三件写进了同一个岗位："Agent、RAG、NL2SQL、权限控制、数据脱敏、日志审计、容器部署、成本和时延优化" `[C]`。**一份岗位同时要求这八件事，本身就是"国内 FDE 是交付岗而不是算法岗"的证据。**

## 四、收不到钱：验收是国内项目的真正终点线

来自一份复盘 3 年央国企 AI 落地的从业者文章，四句原文，一句比一句重要：

- "央国企项目大多分阶段付款，最后一笔款的释放直接挂在验收上" `[A]`
- "验收不仅看产品，还看客户愿不愿意和你一起把这件事做完" `[A]`
- "验收这件事，经常被\'领导问数\'、专家评审、内部 OA 流程反复卡住" `[A]`
- "<b>验收不是末尾，是售前就要规划的事</b>" `[A]`

同一来源还给了一个国内特有的拆分：**交付 = 产品交付（系统能不能跑、能不能用）+ 服务交付（帮客户做标杆、做汇报材料、做成果总结）**，并且警告"服务交付不能替代产品。关系再好，产品差，项目一样会崩" `[A]`。现场环境里还有两条会突然吃掉两周的变量：使用"信创一体机"，以及"大型节假日可能封网" `[A]`。

**终验签字的真实卡点不是技术指标。** 一句被大量转发的现场描述："当乙方拿着一张单薄的《项目验收单》去敲客户技术总监或法务总监的门时，对方却轻飘飘地回了一句：\'我们新换了一位分管领导，对目前的效果还有些新想法，验收先放一放；另外，你们之前承诺的某些非功能指标，好像还没有出具权威的书面证明吧。\'" `[C]`

对立面也摆在这里——一位甲方口径的验收者说，他固定查三样：调用日志（"一个上线三个月的系统，日志是一条平线，说明没人用"）、能叫出名字的用户、以及模型版本和更新记录（"有项目在验收前把大模型悄悄换成了小模型，成本降了八成，能力也降了，合同里没写这一条就查不出来"）；他还点破了指标为什么会赢："指标好写。准确率95%、响应200毫秒，这种数字在PPT上最好写，在验收会上也最难被反驳——因为没人当场复测" `[C]`。

::: warning 关于质保金、双节点验收，只能这样引用
有面向项目甲方的谈判类培训资料（无署名文库文档）给出过"双节点验收（模块初验+整体终验）""15% 质保金 + 18 个月质保"这类档位，并列出"提前释放验收款可能导致供应商后期投入动力不足"的风险 `[C]`。
<b>这些不是国家标准，也不是行业统一惯例。</b>正确写法只有"有培训/谈判资料给出过常见档位"。同样，"缺任一项不签最终验收、不结尾款""功能性 Bug 免费修；新需求走变更单""质保别写\'终身维护\'"这几条来自外包实践 `[C]`，可当 checklist，不能当法规。
:::

## 五、驻场在国内是什么样

不是"坐在客户办公室写代码"。把 JD 正文里的原话并排放在一起，就能看到它的真实形状：

| 原话 | 出处性质 | 等级 |
| --- | --- | --- |
| "长期出差与驻场：根据项目要求，长期驻场在客户现场（时间占比可能高达50%或以上）" | 天津 IT 服务商岗位正文（本站可直读） | `[A]` |
| "同步每日现场交付日报、每周进度复盘台账，同步上线数据、对接记录、权限清单全量交付归档" | ToB AI 服务商 JD 摘要 | `[B]` |
| "快速响应系统卡顿、接口报错、模型调用异常等突发现场技术问题，当日闭环常规故障" | 同上 | `[B]` |
| "配合内部算法团队完成现场大模型适配、RAG知识库本地挂载、Prompt场景化优化、简单智能体工作流编排，无需深度算法研发" | 同上——<b>这一句直接写了岗位边界</b> | `[B]` |
| "联动挖掘二次增购、扩容续约潜在机会" | 同上 | `[B]` |
| "驻场对接客户，深度调研并挖掘客户在AI领域的业务痛点与核心需求" | 软件公司岗位（国聘） | `[B]` |
| "把工程团队拉到业务现场"（安踏、蜜雪冰城、元气森林被这样形容） | 行业访谈式回顾 | `[C]` |
| 产线数据接入需要配合倒班 | 半导体工厂驻场复盘 | `[C]` |

四条读法，全部来自这几张表：**日报与台账是交付物**（不是形式主义，它是你唯一的责任证据）；**"当日闭环"是 SLA**（比任何合同条款都硬）；**"无需深度算法研发"是边界**（承认这一点的人反而少踩坑）；**"挖掘二次增购"意味着你背着商业指标**（面试时一定要问清楚权重）。

## 六、国内这一层的三条自我修养

<div class="mp-steps">
  <div class="mp-step">
    <b>01</b>
    <div>
      <strong>进场第一天，先问"什么数据能出这台机器"</strong>
      <p>这一句比"用什么模型"值钱。答案会决定架构、离线包内容、评审时长，以及你能不能在家办公。<b>答不出来的一律按"全部不出"设计</b>，然后再等人来推翻你——推翻的成本远低于返工。</p>
    </div>
  </div>
  <div class="mp-step">
    <b>02</b>
    <div>
      <strong>把适配清单当交付物，而不是当可行性问题</strong>
      <p>四套指令集 × 六种国产 OS × 五种国产数据库，逐条写"实测过 / 声称支持 / 未知"三态。<b>"未知"这一列的数量就是你项目风险的度量</b>，也是你该收多少钱的依据（报价留 20%–30% 缓冲 <code>[A]</code>）。</p>
    </div>
  </div>
  <div class="mp-step">
    <b>03</b>
    <div>
      <strong>售前阶段就把验收单写好</strong>
      <p>验收清单在 P0 就该存在，而且每一条要能当场复测。这一条同时治三个病：范围蔓延、指标形容词化、以及换领导之后重谈一遍 <code>[A]</code>/<code>[C]</code>。</p>
    </div>
